# Transwitch Visual Engine

## Decision

Transwitch keeps SDL2 as its rendering backend for this iteration. The production launcher already has one SDL window, one SDL_Renderer, renderer-thread texture ownership, SDL_ttf text, and asynchronous CPU-side image decoding. Introducing another UI framework or a second GPU context before isolating these responsibilities would duplicate lifecycle and resource ownership.

Plutonium is useful as a reference for a component-oriented UI layer, but it also uses SDL2 and libnx. It is not added as a runtime dependency in this change.

## First implementation slice

source/VisualEngine.hpp is a non-owning facade over the existing renderer. It centralizes the high-frequency primitives used by the current interface: rectangle fills, rounded rectangle fills, rounded outlines and a cached vertical gradient texture.

Rounded fills are generated by the SDL-independent include/desknx/VisualGeometry.hpp helper and emitted through one SDL_RenderFillRects batch. The gradient ramp is rebuilt only when theme endpoints change. This replaces the old 24-band gradient in each frame with one texture draw.

The engine does not own the window or renderer. All texture creation/destruction and renderer calls stay on the UI/render thread. Existing IconCache workers continue to perform file reads and CPU decoding only. The engine does not change input routing, title launching, modal ownership, workspace persistence, IPC, or sleep/resume code.

## Renderer selection and observability

Startup still tries SDL_RENDERER_ACCELERATED | SDL_RENDERER_PRESENTVSYNC and falls back to SDL_RENDERER_SOFTWARE. The active renderer is queried at runtime; logs record its name, flags, acceleration, software mode, VSync and target-texture support. Therefore the build does not claim GPU acceleration merely because it requested the accelerated flag.

The visual facade tracks its own primitive batches and failures per frame. These counters do not include direct texture operations that have not yet been migrated.

## Next migration stages

1. Move common card, tile, clipping, image-fit and text drawing behind the facade without changing geometry or interaction hitboxes.
2. Introduce reusable visual components (surface, card, game tile, widget frame, button, modal) that consume theme tokens and measured bounds.
3. Add a small animation/tween layer driven by frame delta, with reduced-motion and low-performance fallbacks.
4. Add measured effects only where they improve hierarchy: soft shadows, selected-tile lift, restrained focus transitions and overlay scrims.
5. Use recorded frame metrics on hardware before considering OpenGL ES, custom shaders, or a different backend.

The original v0.1 theme remains available. This foundation is intentionally visual-only and must not alter launcher behavior.
