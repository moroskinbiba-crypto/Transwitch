# Дорожная карта перехода Transwitch к полноценной замене HOME

Статус: архитектурный план. Текущий standalone NRO и текущий HOME applet build — разные режимы запуска; наличие собранного applet не означает, что он уже безопасно и полностью заменяет штатный HOME.

## 1. Что важно перенять у HomeNX и CardsNX

### HomeNX — системная интеграция и состояние приложений

HomeNX разделяет визуальный экран и системную оболочку: верхний OverlayLayer управляет порядком диалогов/быстрых настроек/поверхностей; отдельный backend получает события и системное состояние. Важны не только плитки, но и корректная работа процесса HOME, переключение обратно в приостановленное приложение, жизненный цикл и восстановление после ошибок.

Для Transwitch это означает:
- отдельный Platform/System backend и строгий протокол состояний;
- единая поверхность поверх основного рабочего стола;
- обработка HOME/foreground/background/suspend/resume как событий, а не догадки из истории запусков;
- управление памятью и кэшами с учётом уже работающей игры;
- независимые механизмы установки, отключения и восстановления qlaunch override.

### CardsNX — поведение карточек и управление

CardsNX полезен как UX-референс: крупные карточки и обложки, понятные действия, быстрые системные переключатели, ясные состояния кнопок, контроллерная навигация и предсказуемые переходы. Визуальные идеи следует переводить на общие компоненты Transwitch, а не копировать разрозненные экраны.

## 2. Самое важное изменение: Suspended / Resume — отдельное состояние

Нельзя определять приостановленную игру только по recent.tsv, последнему запущенному title ID или тому, что приложение раньше было открыто. История запусков и реальное состояние foreground/suspended — разные данные.

### Модель состояния

Для текущего foreground-приложения backend должен предоставлять snapshot:

- titleId и тип приложения;
- LifecycleState: Foreground, Suspended, Resuming, Terminating, Unknown;
- время последнего системного события;
- результат последнего перехода;
- доступность системного API, на котором основан snapshot.

Состояние должно обновляться системными событиями/подтверждениями backend. Если источник недоступен, интерфейс показывает Unknown, но не выдумывает Suspended.

### Как выделять приостановленную игру

У игры, которая сейчас действительно приостановлена в системе, должна быть одна заметная метка SUSPENDED или RETURN TO GAME:

- маленький статусный бейдж на обложке, не закрывающий название;
- аккуратная акцентная рамка вокруг соответствующей плитки;
- отдельный быстрый блок Return to game в верхней части HOME, когда есть активная приостановленная игра;
- в подробной карточке — title ID, состояние и последнее подтверждённое системное событие.

Не использовать просто зелёную точку: состояние слишком важно, чтобы обозначать его только цветом. Не помечать одновременно несколько игр как suspended, если backend не подтвердил такое состояние. Для неизвестного состояния использовать UNKNOWN, а не stale badge.

### Launch и Resume — разные команды

- A по обычной плитке — запуск приложения, если оно не является текущим suspended title.
- Resume по подтверждённому suspended title — возврат к существующей сессии, а не повторный запуск нового экземпляра.
- Во время Resuming кнопка блокируется/показывает прогресс; повторные команды дедуплицируются.
- Если resume невозможен, backend сообщает причину; после подтверждённого завершения сессии плитка возвращается в обычное состояние.
- История запусков не может самостоятельно переводить игру в Suspended.

## 3. Изменения архитектуры перед переходом

### Этап 0 — Shell/API separation

Разделить текущую большую main.cpp на:
- ShellView — визуальная композиция рабочих столов/дока/панелей;
- SurfaceManager — стек модальных поверхностей и единый backdrop;
- WidgetRuntime — виджеты, snapshots и действия;
- ArtworkRuntime — SGDB/custom art/icon cache;
- SystemBackendClient — системный IPC и состояние приложений;
- StandalonePlatform и HomeAppletPlatform — разные платформенные адаптеры.

UI не должен сам напрямую решать, что игра suspended, менять system flags или запускать скрытые system services. Он запрашивает команды backend и отображает подтверждённые ответы.

### Этап 1 — Lifecycle backend

Добавить сообщения/события:
- ForegroundChanged;
- ApplicationSuspended;
- ResumeRequested;
- ResumeCompleted;
- ApplicationTerminated;
- LifecycleSnapshot;
- LifecycleUnavailable.

Требования: версии протокола, валидация ID, таймауты, heartbeat, deduplication, журналирование и тесты переходов. Один источник истины для текущей игры и состояния HOME.

### Этап 2 — HomeApplet runtime

Подготовить отдельный режим запуска HOME applet:
- правильный тип applet и системный жизненный цикл;
- совместимые с целевой прошивкой libnx/Atmosphère интерфейсы;
- корректное получение/освобождение системных сервисов;
- обработка event loop при возврате из игры и системных апплетов;
- ограниченные ожидания и корректные fallback при недоступности сервиса.

Нельзя считать обычный NRO эквивалентом штатного HOME: у HOME процесса другие ограничения памяти, приоритеты и переходы жизненного цикла.

### Этап 3 — Память и ресурсы при приостановленной игре

При наличии живой игры Transwitch не должен рассчитывать на ресурсы, доступные обычному самостоятельному приложению:
- bounded GPU texture cache;
- очистка дальних обложек и preview перед возвратом/переходом;
- ограничение размера и количества decoded images;
- отсутствие тяжёлой синхронной работы на startup/resume;
- безопасное восстановление после неудачной аллокации;
- отдельные профили для handheld/docked и разных размеров памяти.

Ресурсный бюджет нужно измерять на реальной консоли с тяжёлыми играми, а не выводить из host CI.

### Этап 4 — HOME UX

- Плитка suspended game с явным состоянием и действием Resume.
- Уведомления о состоянии контроллеров, сети и системных событиях.
- Быстрый доступ к профилю, альбому, настройкам, питанию и контроллерам.
- Единый modal/surface stack с предсказуемым фокусом и blur/dim.
- Плавное возвращение к workspace после закрытия системных апплетов.
- Сохранение последнего рабочего стола и позиции фокуса без гонок с launch/resume.

### Этап 5 — Installer / recovery

Замену HOME нельзя выкатывать как обычное обновление NRO. Нужен отдельный транзакционный установщик:
- резервная копия оригинального qlaunch/override и проверка целостности;
- манифест файлов и версий;
- запись во временную область, проверка, затем атомарная публикация;
- режим восстановления, который может отключить override без загрузки Transwitch UI;
- безопасный uninstall и восстановление предыдущих файлов;
- ручной opt-in на первый переход и подтверждение совместимости Atmosphère/HOS;
- запрет на продолжение установки при неизвестном/изменённом существующем override без явного подтверждения.

Пока recovery path не доказан на консоли, установка полного HOME replacement должна оставаться opt-in/experimental.

## 4. Предлагаемая последовательность перехода

| Этап | Результат | Критерий завершения |
|---|---|---|
| A. Standalone hardening | Обычный NRO остаётся надёжной тестовой оболочкой | Нет блокировок, сохранение/кэш/виджеты стабильны |
| B. Platform abstraction | Один UI, два платформенных адаптера | Host tests и NRO build проходят для обоих режимов |
| C. Lifecycle backend | Системно подтверждённые foreground/suspended состояния | Тесты переходов и реальный resume на Switch |
| D. HOME applet prototype | HOME applet запускается/закрывается под управлением backend | Возврат к приостановленной игре без повторного запуска |
| E. Recovery installer | Транзакционная установка и удаление | Проверены crash/power-loss/recovery сценарии |
| F. Opt-in replacement | Пользователь может включить замену штатного HOME | Длительная аппаратная проверка на нескольких сценариях |

## 5. Обязательные аппаратные тесты перед stable

1. Открыть HOME из работающей игры, убедиться в Suspended, затем выполнить Resume и подтвердить возврат к той же сессии.
2. Повторить с тяжёлой игрой при почти заполненной памяти/кэше.
3. Проверить Homebrew, системные апплеты, альбом, клавиатуру, контроллеры, пользователя, питание и сеть.
4. Проверить handheld ↔ docked и подключение/отключение Joy-Con/Pro Controller.
5. Принудительно завершить Transwitch и проверить, что штатный HOME/recovery доступен.
6. Отключить SD/повредить конфигурацию и убедиться, что приложение не перезаписывает корректные backups.
7. Проверить реальный холодный старт, sleep/wake и повторное открытие HOME.

**Решение:** полноценная замена HOME — это не «добавить ещё один экран». Это переход Transwitch из standalone homebrew приложения в системную оболочку с надёжным backend, жизненным циклом приложений, Resume semantics и независимым механизмом восстановления.
